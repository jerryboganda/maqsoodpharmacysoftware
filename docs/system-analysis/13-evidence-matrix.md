# 13 — Evidence Matrix (Audit Trail for the Whole Analysis)

**Document purpose.** This is the **audit trail** for the WASEELA ABUZAR V3 analysis. Every load-bearing conclusion produced in documents `00b` and `02`–`11` is recorded here as a single traceable row: what was concluded, how strongly it is supported, which document carries the argument, which code object or database object is the primary evidence, and how confident we are. Nothing in the modernization plan should rest on a conclusion that does not appear here. If a reviewer disagrees with a row, they can go straight to the cited object and check it.

**Analysis stage.** Stage 4 — *Consolidation*. All domain analysis passes (repository map, module catalog, screen inventory, sales & purchase workflows, database, accounting, inventory, roles/permissions, reports, integrations, data profile) are complete. This document is derived **entirely** from those completed passes plus the binding owner decisions in `00b-owner-decisions-and-requirements.md`. No new investigation was performed to produce it.

**System under analysis.** WASEELA ABUZAR V3 — compiled Sybase/SAP PowerBuilder 12.5 32-bit Windows desktop application over Microsoft SQL Server, deployed at a single retail pharmacy ("Fazal Din PP19", Gujranwala, Pakistan). Data window 2025-01-01 → 2026-07-31. Currency PKR.

> ⚠️ **THE EXISTING SYSTEM WAS NOT MODIFIED.** Every finding recorded here was obtained by read-only means: `SELECT`/metadata queries against the live database under explicit owner authorization (decision **D2**), offline reading of `extracted_scripts.sql` / `db_modules_full.sql`, and string/object extraction from the compiled `.pbd` binaries. **No `INSERT`, `UPDATE`, `DELETE`, `ALTER`, `DROP` or `CREATE` statement was executed. No application file was edited. No configuration was changed. No data was deleted or archived.** The pharmacy traded normally throughout the analysis — row counts visibly moved between passes (see `EV-DAT-14`), which is itself proof the system stayed live and untouched.

## Evidence-label legend

| Label | Meaning | What it takes to earn it |
|---|---|---|
| **Verified** | Read directly from primary evidence and reproducible. | A live query result, a quoted stored-procedure/function body, a schema definition, or a literal string extracted from a binary. |
| **Strongly Inferred** | Not stated anywhere explicitly, but two or more independent lines of evidence converge and no evidence contradicts it. | e.g. an empirically validated formula, or a naming convention corroborated by contents. |
| **Unclear** | The evidence is ambiguous or contradictory; a human must resolve it. | Two plausible readings, no tiebreaker in the data. |
| **Missing** | The evidence does not exist and cannot be recovered from what we hold. | e.g. compiled event-script bytecode; pre-2025 history. |
| **Deprecated** | Present in the product but superseded, dead, or a legacy artefact. | Duplicate procedures, migration staging tables, retired code paths. |
| **Broken/Incomplete** | Present and reachable, but demonstrably defective. | A quoted defect in shipped code, or a guard that cannot fire. |
| **Recommended** | A **proposal for the NEW system**. **NEVER an existing feature.** | Nothing in the legacy system supports it; it is our design advice. |
| **Owner-confirmed** | Stated directly by the business owner; overrides inference. | Recorded in `00b` decision log D1–D12. |

**Confidence** is a separate axis from the label. It answers *"how likely is this to survive scrutiny or change under new information?"* — **High** = would take contradicting primary evidence to overturn; **Medium** = plausible but resting on one line of evidence, a sample, or an unresolved question; **Low** = a working assumption we would not bet the plan on.

**ID scheme.** `EV-<DOMAIN>-<n>`. Domains: `SYS` system/architecture · `MOD` modules · `SCR` screens/forms · `WFS` sales workflows · `WFP` purchase workflows · `DB` database · `ACC` accounting · `INV` inventory · `SEC` roles/permissions/security · `RPT` reports · `INT` integrations · `DAT` data profile · `OWN` owner decisions & requirements.

**Row count: 329**, distributed across the 13 domains as shown in §15. Section 14 lists **every** row whose confidence is Medium or Low (37 rows, 11%), grouped by *why* it is soft and what would firm it up, so reviewers can see exactly which parts of the plan rest on softer ground.
