# 21 — Feature Traceability Matrix (Old System → New System)

**System analysed:** WASEELA ABUZAR V3 — Sybase PowerBuilder 12.5 (32-bit) + Microsoft SQL Server, deployment **"Fazal Din PP19"**, Gujranwala, Pakistan.
**Target system:** Node.js + TypeScript backend · React + TypeScript frontend · MySQL 8 · REST API · modular monolith.
**Analysis stage:** Stage 21 — Feature Traceability & Disposition (the gate document between analysis and build planning).
**Date:** 2026-08-02.

---

## Document purpose

This document exists to guarantee **one thing**: that **no feature of the existing system disappears silently**.

Every module, screen, workflow, report family, integration, device, background job, audit artefact and legacy relic discovered during Stages 02–11 appears in exactly one row below, with an explicit, named disposition. If a capability is being dropped, this document is where that decision is recorded, with the evidence it was based on and the approval it still needs. If a capability belongs to a non-pharmacy vertical, it is **catalogued and deferred** (owner decision **D1**) — never deleted from the record.

It is also the reverse index: for every capability planned in the new system, this document states whether it replaces something that exists today, or is genuinely new (`Recommended`).

**Two audiences.** The *Existing Feature*, *Business Purpose* and *Current Status* columns are written for the business owner. The *Evidence*, *New Module*, *Migration Requirement* and *Test Requirement* columns are written for the engineering team.

## The existing system was NOT modified

All analysis behind this matrix was **read-only**. Authorised under owner decision **D2** (SELECT / metadata introspection only). No schema change, no data change, no stored-procedure change, no file change was made to `FazalDinPP19DataBaseV2`, to `E:/Pharma Software/V2_AbuzarSoftware/`, or to any running component of the legacy system. The live pharmacy continues to operate on the legacy stack unaffected.

## Evidence-label legend

Applies to the **Current Status** column, which describes **the existing system only**.

| Label | Meaning |
|---|---|
| **Verified** | Read directly from a stored procedure, trigger, view, schema object, `.pbd` string inventory, or live row counts. Cited in the Evidence column. |
| **Strongly Inferred** | Multiple independent evidence sources converge; no single direct read. |
| **Unclear** | Evidence is ambiguous or contradictory. Requires human confirmation before a build decision. |
| **Missing** | The capability is expected in a system of this kind but no evidence of it exists. |
| **Deprecated** | Superseded artefact of a prior system or prior version, still present. |
| **Broken/Incomplete** | Present but demonstrably non-functional, half-wired, or defective. |
| **Dormant** | The product ships it and the code paths exist, but it carries **zero business rows** at Fazal Din PP19. *An empty table proves non-use here — never absence from the product.* |
| **Recommended** | A proposal for the **NEW** system. **Never** a statement about the existing system. Used only in the *Modern Decision*, *Migration Requirement* and *Test Requirement* columns, and for every row in §12. |

> **Rule enforced throughout:** anything said about the new system is `Recommended`. No recommendation is ever presented as an existing feature.

## Modern Decision vocabulary (closed set)

Every row uses exactly one of these ten. All are `Recommended`.

| Decision | Means |
|---|---|
| **Retain unchanged** | The *behaviour contract* is preserved exactly — same formula, same numbers, same payload. Implementation language changes; semantics do not. Reserved for things that must reconcile byte-for-byte or rupee-for-rupee. |
| **Retain with technical rewrite** | Same capability, same business rules, rebuilt on the new stack with modern UI, validation and tests. |
| **Simplify** | Capability kept, surface area cut (fewer fields, fewer variants, fewer settings). |
| **Redesign** | The business need is kept but the mechanism is replaced because the current one is broken, unsafe, or architecturally wrong. |
| **Merge** | Folded into another feature; ceases to exist as a separate thing. |
| **Split** | One overloaded artefact becomes several properly-bounded ones. |
| **Deprecate** | Not built in v1. Data model and this record are retained so it can be built later without re-analysis. |
| **Remove after approval** | Proposed for deletion. **Requires written owner sign-off before removal.** Archived first where data exists. |
| **Requires clarification** | Cannot be dispositioned without an answer from the owner, accountant, pharmacist or vendor. Blocking. |
| **Defer (non-pharmacy vertical)** | Belongs to a vertical this pharmacy does not run (hospital, school, HR, hotel, manufacturing, multi-branch). **Catalogued, explicitly NOT dropped** — owner decision **D1**. |

**New capabilities (§12)** carry the decision **New — Recommended**, meaning *no existing equivalent*.

## How to read a row

- **Evidence** cites the analysis document section plus at least one of: table, stored procedure, `.pbd` library, or preference key.
- **Migration Requirement** states what must happen to *data* at cutover. `None` means no data moves. Financial opening balances are **zero** at cutover (**D10/R3**); physical stock **carries over** (**D11/R3.3**); 19 months of history (2025-01-01 → 2026-07-31) migrates (**D3/R3.2**).
- **Test Requirement** states the acceptance check that proves the disposition was honoured.
